# M2.5 report: hardening and soak

Date: 2026-10-13/14. Same Windows 11 laptop as M1/M2 (i5-12450HX, Realtek mic array and speakers). The plan is in [roadmap.md](roadmap.md) §3.

## Summary

| Item | Result |
|---|---|
| Echo-gate onset | **Changed approach after measurement.** No audio-level signal decides safely within about 1 s on this hardware. The gate now reports `EchoState`, and mic speech that may contain unremoved echo is flagged `echo_unverified` for the M3 transcript check. |
| Silence-fill cap | `GapFillPolicy`: at most 300 s of gap silence per capture session; then `GapFillBudgetExhausted`, gaps are left as gaps, and the device stream is reopened once |
| Stall watchdog | `StallWatchdog`: 2 s without packets → `Stalled` and the stream is reopened. Loopback counts only while the endpoint meter shows audio. **Verified live** with fault injection. |
| Disk tiers | `DiskPolicy`: warn below 500 MiB, pause writes below a 50 MiB reserve (audio waits in the queue), resume at 100 MiB |
| Session limit | Optional `SessionLimit`: warning before the limit and an event at the limit; the application decides whether to stop |
| Soak | **4 h on real devices: nothing lost, memory flat, 9 % of one core.** The first soak found a memory leak in the VAD; it is fixed. |

## Echo-gate onset: measurements and decision

In M2's live double-talk run (A2), the gate engaged 3.3 s after the far end started, and 1.3 s of far-end speech was detected as mic speech. Two faster signals were measured on the three live recordings: A2 (real echo), A (driver echo cancellation, i.e. independent talkers) and B (music).

| Signal (1–2 s windows) | Real echo (A2, music) | No echo, double talk (A) |
|---|---|---|
| Envelope correlation, max | 0.74–0.86 | **0.64–0.76** |
| AEC3 linear-filter reduction in the first 3 s | 0.2–3.4 dB | about 0 dB, but the echo is only ~5 dB above the raw mic's noise floor here |

- **The two cases overlap.** A threshold fast enough to catch A2 would switch AEC on during ordinary double talk for headset users, and M2 showed that degrades near-end speech.
- **Starting with AEC on** (a remembered "echo present" state per device pair) removed the A2 leak. But with a wrong prior on A it trimmed 0.5 s of the user's speech. Many laptops also keep the same endpoint id when headphones are plugged into the jack, so a per-device prior is unreliable.

**Decision:**
- The gate keeps its conservative rule and now exposes `EchoState::{Unknown, Echo, NoEcho}`.
- `RecorderEvent::Speech` gained `echo_unverified`: part of the segment fell where the far end was active while the state was still `Unknown`.
- Reprocessing the recordings:

  | Recording | Flagged segments |
  |---|---|
  | A2 | The leaked far-end segment (15.6–16.9 s) and the onset of the user's double-talk reading |
  | A | The first user reading, made before the gate decided |
  | Music, mic-only recordings | Nothing |
- **The flag means "check", not "drop".** M3 compares flagged mic text with the system transcript. Echo will match; real speech won't.

The acceptance criterion "0 false mic speech segments on the M2 script" therefore moves to M3, at transcript level.

## Soak

**Setup** ([tools/soak](../tools/soak/README.md)):
- `sdctl record --process --agc --restart-every 1800` for 4 h on the real default devices, overnight with the user asleep (a quiet room).
- An inaudible noise file (−70 dBFS) played continuously so the system stream carried real audio and clock. It was relaunched every 60 s.
- Every 30 min a forced device restart (7 per source).
- The recorder's resources logged every minute.
- The audio was deleted after analysis, as agreed. The resource log is [data/m2.5-soak-resources.csv](data/m2.5-soak-resources.csv).

### Run 1: found a leak

Private memory grew steadily, about 2 MB per minute ([data/m2.5-soak-leaky-resources.csv](data/m2.5-soak-leaky-resources.csv)):

| Elapsed | 1 min | 10 min | 20 min | 27 min |
|---|---|---|---|---|
| Private memory | 33.1 MB | 52.4 MB | 73.8 MB | 88.8 MB |

**Isolation** (`examples/leakprobe`, the recorder on synthetic audio at 20× real time, 20 min of audio each):

| Mode | Private memory |
|---|---|
| Journal only | 4.5 → 5.8 MB |
| Plus AEC/AGC processing | 8.6 → 8.9 MB |
| **Plus Silero VAD** | **37 → 75 MB** |

**The VAD alone** (`examples/vadmem`, 30 min of audio each) leaked about 0.75 MB per minute of audio per VAD instance, about 400 bytes per inference. These changes made **no difference**:
- disabling ONNX Runtime's CPU arena;
- disabling memory-pattern optimisation;
- disabling graph optimisation;
- passing inputs as zero-copy views.

**Binding the two outputs to tensors allocated once fixed it** (21 MB flat). Probabilities are bit-identical to before (new test) and VAD accuracy is unchanged (F1 0.976 clean, 0.950 at 0 dB SNR). The full recorder with VAD then stayed at 33.4 → 34.0 MB over 40 min of audio.

Run 1 was stopped by killing the process, which doubled as a crash test. The journal recovered 1,794.7 s per source with 0 gaps and 0 rejected records.

| Metric | Result |

| Device restarts | 7 per source; all recovered |
| Private memory | 30.8 MB at 1 min, **31.0–32.0 MB from 30 min to 4 h** (flat) |

| Handles / threads | 271–278 / 8–10, no growth |

### Open items from the soak

- **Reference realignments at loopback resume.** The processing stage counted **458** of them: realignments of more than 2 ms, about two per noise-player relaunch. Its smoothed reference-rate reading ended at 57 ppm, against a measured clock difference of −0.7 ppm, so the idle/resume transitions bias it. Audio is never lost by this, and each realignment is instantaneous. It is the same idle/resume path that M2 noted, and it should be examined before M3 measures echo cancellation on real meetings, which pause and resume system audio constantly.
- **Not a full-pipeline soak.** Transcription and diarization (M3/M4) will add CPU and memory load. The roadmap keeps an 8 h full-pipeline soak after M4.
- **A quiet overnight room and synthetic system audio.** The recording volume and content were unlike a real meeting.
